## 1. Phone `connectedDebugAndroidTest` fails while every test passes

**Result: tooling defect in AGP 9.4.1's bundled test runner, not a test, install, instrumentation, report or cleanup failure. No repository change fixes it; the Gradle verdict on a `host:port` ADB serial carries no information.**

Reproduced with the smallest run (`:core:export-pipeline:connectedDebugAndroidTest`, class `AlphaContractDeviceTest`, `--info`): Gradle exit **1**, `There were failing tests`, while the XML reports `tests="4" failures="0" errors="0" skipped="0"` and every test case in `test-result.pb` carries the same PASSED status (3) as the green emulator-5554 runs. The `--info` log shows each step succeeding in order: install (`adb install … -t -g`), `am instrument -r -w …`, XML generation, additional-output and coverage collection, uninstall of `com.akane.akastudio.core.export.test`; no error is logged before `Task … FAILED`.

Root cause, from the bytecode of `com.android.tools.utp:gradle-work-action:32.4.1` (`AndroidTestEngineRunner`, `DeviceTrackingListener`) and `com.android.tools.androidtest:android-test-engine:1.0.1`:

1. The engine builds JUnit-platform unique ids `[engine:android-test-engine]/[device:<serial>]/…`. JUnit (`junit-platform-engine` 1.13.3, `UniqueIdFormat`) URL-encodes `:` inside a segment value, so the phone's segment is `[device:100.70.96.59%3A5555]`.
2. `DeviceTrackingListener` keys its `perDeviceAllTestsPassed` map by the text after `[device:` — `100.70.96.59%3A5555`.
3. `AndroidTestEngineRunner` then looks up each run config's raw `deviceSerialNumber` (`100.70.96.59:5555`), gets `null`, treats it as `false`, writes `1` to `test-result-exit-code.txt`, and AGP (`UtpTestUtils.runUtpTestSuiteAndWait`) reports "There were failing tests".

A serial without `:` (`emulator-5554`) round-trips unchanged, which is why the emulator runs exit 0. A JVM check with the same JUnit jar prints `100.70.96.59:5555 -> key=100.70.96.59%3A5555 equalsSerial=false` and `emulator-5554 -> key=emulator-5554 equalsSerial=true` (`gradle-tcp-serial/Uid.java`). `-Pandroid.experimental.androidTest.useUnifiedTestPlatform=false` does not switch AGP 9.4.1 off this engine (same engine, same exit 1). Because the lookup always misses, a real failure on the phone also exits 1, so Gradle cannot distinguish pass from fail here.

Not done, by rule: no `ignoreFailures`, no exit-code suppression, no filtering wrapper, no AGP bump. Phone results are read from the XML (`TEST-*.xml`) or the raw `am instrument -r` stream (`INSTRUMENTATION_STATUS_CODE` per test, final `OK (n tests)` / `FAILURES!!!`). Upgrading AGP or a mDNS (colon-free) serial would be the real fixes; both are outside this task. Evidence: `gradle-tcp-serial/alpha-info.log`, `alpha-legacy.log`, `prior-export-connected-20261101/`, `rerun-results/`.

## 2. L1 and C1 memory / thermal cost

**Method.** New manual probe `app/src/androidTest/.../studio/PhysicalMemoryProbeDeviceTest.kt` (skipped unless `qaMemoryInputDir` is passed, so normal suites only report it as skipped; SHA-256 of the version that ran: `a051deb3…9729`). It runs in the real app process on physical display 0 with the real ViewModel, MediaStore uris, curator models, GL renderer and export. Inputs: six licensed natural travel photos at phone resolution (3201×5230 to 4912×3264, 11–17 MP; Wikimedia Commons, CC BY / CC BY-SA; hashes and attribution in `memory/mem-input-manifest.json`), inserted twice as distinct MediaStore rows (set A, set B, same bytes). Each import starts from the curator's suggested look with HDR Boost off (an import replaces the studio state), so every swap and the control are prepared identically; MEDITERRANEAN_AZURE + HDR Boost are applied after a story is Ready and so cover the Ready idles and all exports (UHD 2160×3840). Recorded:

- exact per-phase **peak RSS**: VmHWM after resetting it through `/proc/self/clear_refs` (resets took effect: e.g. the Ready idle reads 557 MiB right after a 702 MiB prepare peak);
- RSS every 50 ms from `/proc/self/statm` (shorter spikes show only through VmHWM);
- at each phase boundary `/proc/self/status` and `Debug.MemoryInfo`;
- host `dumpsys meminfo` about every 1.3 s (PSS, RSS, Java, Native, Graphics = GL mtrack + EGL mtrack; shorter GPU peaks can be missed), thermal status and battery temperature every 5 s, focused window every 3 s.

Constant offsets in every value: the instrumentation's classes and the ~29 MiB of input bytes the probe keeps in memory. Each export phase also reads its 2–3 MB output file inside the measured window. Run 1: 4 swaps, 3-export burst, 10 s idles (228.5 s, OK 1/1). Run 2 (fresh process): 2 swaps, 1-export burst, 6 s idles (124.7 s, OK 1/1). AkaStudio held focus in every in-run sample except one `null` during launch (run 1 70/71, run 2 38/38). Exports were checked (Social: no `hdrgm`; Ultra: MPF + `hdrgm`) and deleted with the input rows; no `Pictures/AkaStudioQA/mem_*` rows remain (`device-facts.txt`).

**L1 conclusion.** In the user-reachable swap from a Ready story, the retired story's photos were already released when the replacement started decoding: the first 50 ms sample of every swap is at the empty-studio level, and every swap's exact peak RSS is within 2.3 MiB of the discard-then-import control across six swaps in two processes (the control ran last, so slow creep favours it reading highest). RSS after each swap creeps by under 1 MiB per swap. This covers RSS (CPU-side photo bitmaps); GPU memory is sampled only every ~1.3 s, and in run 1 swap 4 left an unexplained +94 MiB of GL mtrack (329.7 → 423.7 MiB) that stayed until the re-import. The schedule in which overlap is possible (retired cleanup delayed behind a cancelled in-flight prepare or export) was not exercised; there the extra would be at most one prepared story, measured here at about 95 MiB RSS plus its textures. Classification: bounded design property, not a verified defect; no fix.

**C1 conclusion.** With the same story and settings, Ultra HDR peaks 105–183 MiB above Social (820–898 vs 715 MiB peak RSS), and its Java heap peaks at 338–371 MiB versus about 236 MiB. That difference contains everything the Ultra path adds over Social (boosted frame, SDR base, scalar gain, encode buffers), not only C1's increment over C4. The reported ≈+37 MiB (compute log/code arrays) plus 7.4 + 7.4 MiB gain plane/staging versus C4 was a logical allocation estimate; a production build cannot isolate it (that would need a C4 build, which M1 does not reopen), so these measurements bound it from above and do not confirm 37 MiB. Each export settled within about 6 MiB of its pre-export RSS after lazy GC (~10 s), and consecutive Ultra exports did not accumulate. Largest peak 898 MiB RSS on a phone with MemTotal 10.85 GiB; no OOM and no low-memory kill (the event log shows only `finished inst` stops). The tightest margin is the Java heap: with `largeHeap` the limit is 512 MiB, and Ultra exports peaked at 66–73 % of it. That is a margin to watch on smaller-heap devices, not a failure here.

**GPU memory (new, bounded, cause not isolated).** Graphics (mostly GL mtrack) is 58 MiB at launch and ~342 MiB with a Ready story; it rises to 623–944 MiB during exports and falls on the final discard (716 → 601 and 687 → 601 MiB), but both runs end at 601 MiB after discard, about 260–280 MiB above a fresh discard without exports (run 2: 323 MiB). It does not grow with more exports (run 1: 5 exports, run 2: 3; same end value). The app already frees export grades and free framebuffers after each export (`GlStoryRenderer.renderOffscreen`), so the remainder is either preview grade/texture caches or the Adreno driver's per-process pool. `am send-trim-memory … HIDDEN` is refused for a foreground process, so the cause was not separated. Not a leak by this evidence; open measurement.

**Thermal.** Thermal status 0 (none) in all samples of both runs. Battery temperature (live) 33.8 → 32.5 °C (run 1) and 31.9 → 32.1 °C (run 2); battery 78 → 77 %, not charging. The thermal service's "Cached temperatures" (AP 54.1, SKIN 37.7 °C) never changed, so they are stale and not used. Live HAL values at 03:45, ten minutes after run 2: AP 32.9, SKIN 33.0, BAT 31.1 °C (`device-facts.txt`). Export times show no monotonic slowdown across the burst (10.3–12.4 s). No stress test was run.

**Probe limitations found by review** (not changed after the runs, so the code matches the evidence): the discard phase ends at the state flip, before cleanup; `resetHwm` accepts a reset when VmHWM ≤ VmRSS + 4 MiB rather than comparing before/after; inserts and the activity launch sit before the `try`, so a mid-insert failure or a process kill can leave QA rows (host cleanup by `RELATIVE_PATH` covers it); the gain-map check is a substring test, not an MPF parse; the control always runs last.
